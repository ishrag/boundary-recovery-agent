When AI actions cross system boundaries

The action succeeded. The agent never found out.

An AI agent can crash after an external system commits an action but before the acknowledgement is saved. Retrying may duplicate the action. Stopping may leave the workflow unfinished. BOUNDARY resolves that uncertainty before the agent acts again.

The problem

A timeout creates two dangerous choices.

The agent cannot safely continue until it learns what the external system actually did.

01 · BLIND RETRY

Repeat the action

If the first action already committed, a retry can create duplicate orders, notifications, payments, or workflow steps.

02 · BLIND STOP

Abandon the workflow

If the request never reached the provider, stopping leaves the requested work incomplete with no safe resolution.

03 · BOUNDARY

Reconcile, then decide

Preserve the original intent, inspect authoritative provider evidence, permit only the safe tool, and verify the result.

The solution

Recover from evidence—not assumptions.

BOUNDARY separates probabilistic diagnosis from deterministic permission. The model proposes what happened; the safety gate decides what the system is allowed to do.

Persist intentSave the operation identity and payload before dispatch.
Reconcile outcomeQuery independent provider evidence after an interruption.
Fail closedBlock mutations until identity, receipt, and state checks pass.
Agent workflow

Five stages. One controlled decision.

The recovery agent gathers evidence, diagnoses the incident, selects an allow-listed strategy, acts only through policy, and verifies the resulting state.

01ObserveCollect durable local and provider evidence.
02DiagnoseRank the likely incident causes.
03PlanChoose an allow-listed recovery strategy.
04ActExecute the permitted lookup or repair.
05VerifyCheck final state and detect duplicates.

Important: “Act” does not automatically mean “retry.” For an uncertain outcome, the safest action may be a read-only reconciliation lookup.

How BOUNDARY handles a failing system The project demonstrates the full recovery loop required for a failing system: identify the incident, diagnose its cause, perform or block corrective action, and verify the outcome.
Identify

Detects a durable request with no trusted local outcome.

Diagnose

Classifies the incident from logs, receipts, state, and effect counts.

Correct

Selects a safe lookup, same-key retry, wait, or escalation.

Verify

Checks the receipt, final state, version, and duplicate count.

Resilience checks

Beyond the happy path

  • Concurrent recoveryOne lease owner acts while other workers observe the result.
  • Concurrent executionOnly one dispatch is accepted for the protected operation.
  • Process restartRecovery is exercised before and after provider commit.
  • HTTP process boundaryA full recovery crosses the separate provider service.
  • Idempotency-key misuseA reused key with a different payload is rejected.
Lessons

What the prototype established

  • Unknown is a third state.It is neither success nor failure and must be reconciled.
  • Idempotency is necessary, not sufficient.The agent still needs authoritative evidence before retrying.
  • Diagnosis and permission must be separate.The model proposes a cause; deterministic policy authorizes every write.
Honest limitations

What this MVP does not claim

  • The domain is a controlled order-reschedule demo with injected failures.
  • The local diagnosis model uses a small synthetic case set, not production incident data.
  • SQLite and the lease design are single-node MVP components.
  • Demo APIs do not yet include production authentication or tenant isolation.
  • The result above is the latest published run, not continuous production monitoring.
